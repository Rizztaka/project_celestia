# **Project Celestia Development Guide**

**Document Version:** 1.0

**Status:** Active

**Last Updated:** July 2026

\---

## **Purpose**

This document defines the engineering standards, coding conventions, and implementation rules for Project Celestia.

Every implementation, whether written by a human or generated by AI, must follow these standards.

If an implementation conflicts with this guide, this document takes precedence unless a newer version has been formally accepted.

\---

## **Core Engineering Philosophy**

Project Celestia values:

- Correctness over speed.
- Readability over cleverness.
- Maintainability over shortcuts.
- Simplicity over unnecessary complexity.
- Consistency over personal preference.
- Long-term scalability over quick fixes.

Every contribution should leave the codebase cleaner than it was before.

\---

## **General Rules**

### **Rule 1 — Single Responsibility**

Every file, class, component, and function should have one clear responsibility.

If a file starts solving multiple unrelated problems, split it.

\---

### **Rule 2 — Feature First**

Code should be organized by feature/domain, not by technical layer alone.

Prefer:

games/genshin/teams/

instead of:

controllers/

services/

models/

at the project root.

\---

### **Rule 3 — Avoid Duplication**

Duplicate logic should be extracted into shared utilities or reusable components.

Never copy and paste business logic.

\---

### **Rule 4 — Composition Over Inheritance**

Favor reusable composition patterns instead of deep inheritance hierarchies.

\---

### **Rule 5 — Keep Functions Small**

Functions should be focused and easy to understand.

If a function becomes difficult to explain, split it into smaller functions.

\---

## **TypeScript Standards**

- Strict mode must remain enabled.
- Avoid the "any" type whenever possible.
- Define explicit interfaces for public APIs.
- Reuse shared types from the monorepo.
- Prefer type safety over convenience.

\---

## **Backend Standards**

Controllers should:

- Validate requests.
- Call services.
- Return responses.

Controllers should not contain business logic.

Services contain business rules.

Repositories handle database access.

Calculation modules should remain pure whenever practical.

\---

## **Frontend Standards**

Components should be:

- Reusable
- Accessible
- Small
- Predictable

Large components should be divided into smaller pieces.

Business logic should not live inside UI components unless it is purely presentation-related.

\---

## **State Management**

### **TanStack Query**

Responsible for:

- API communication
- Server state
- Caching
- Synchronization

\---

### **Zustand**

Responsible for:

- UI state
- Theme
- Local preferences
- Temporary selections

Never duplicate server state inside Zustand.

\---

## **API Standards**

Every endpoint must:

- Validate input.
- Return consistent response structures.
- Handle expected errors gracefully.
- Use meaningful HTTP status codes.

Example success response:

{

&#x20; "success": true,

&#x20; "data": {},

&#x20; "message": ""

}

Example error response:

{

&#x20; "success": false,

&#x20; "error": {

&#x20; "code": "VALIDATION\_ERROR",

&#x20; "message": ""

&#x20; }

}

\---

## **Validation**

Never trust client input.

Validate:

- Request body
- Query parameters
- Route parameters
- Authentication
- Authorization

Every validation error should produce a helpful message.

\---

## **Error Handling**

Errors should:

- Be descriptive.
- Avoid exposing sensitive information.
- Be logged appropriately.
- Return consistent formats.

\---

## **Performance Guidelines**

Do not optimize prematurely.

Optimize only after profiling identifies a measurable bottleneck.

Examples of future optimizations:

- Redis caching
- Worker queues
- Background jobs
- Streaming
- WebSockets

These should only be introduced when justified.

\---

## **Intelligence Core Standards**

Recommendation systems must:

- Produce deterministic results whenever possible.
- Explain every recommendation.
- Avoid hidden scoring systems.
- Clearly separate calculations from explanations.

Artificial intelligence should enhance understanding rather than replace reliable algorithms.

\---

## **UI Principles**

The interface should always feel:

- Clean
- Fast
- Consistent
- Responsive
- Accessible

Avoid unnecessary animations or visual clutter.

Every screen should clearly communicate its purpose.

\---

## **Naming Conventions**

Folders:

- lowercase
- kebab-case where appropriate

Files:

- descriptive
- consistent
- feature-oriented

Functions:

- verb-based
- clearly describe their purpose

Variables:

- meaningful names
- avoid abbreviations unless universally understood

\---

## **Documentation Standards**

Every major feature should include:

- Purpose
- Inputs
- Outputs
- Dependencies
- Future improvements

Architectural decisions should be recorded in "DECISIONS.md".

\---

## **Testing Philosophy**

Critical business logic should be testable.

Pure functions are preferred because they are easier to verify.

Tests should prioritize:

- Recommendation logic
- Calculations
- Validation
- API behavior

\---

## **Code Review Checklist**

Before considering any feature complete, verify:

- Project builds successfully.
- No TypeScript errors.
- No ESLint errors.
- Feature follows architecture.
- No duplicated logic.
- Code is understandable.
- Validation exists.
- Error handling exists.
- Documentation updated.
- Tests added where appropriate.

\---

## **AI Collaboration Rules**

When using AI tools such as Gemini:

- Do not generate multiple unrelated features in one prompt.
- Work one milestone at a time.
- Preserve existing architecture.
- Ask questions instead of making assumptions.
- Explain architectural trade-offs.
- Avoid introducing unnecessary dependencies.
- Do not rewrite stable code without justification.

\---

## **Development Workflow**

Every feature follows this process:

1\. Plan.

2\. Review requirements.

3\. Implement.

4\. Test.

5\. Review architecture.

6\. Improve.

7\. Update documentation.

8\. Merge.

Do not skip review simply because the code works.

\---

## **Definition of Done**

A feature is considered complete only when:

- Functionality is implemented.
- UI is complete (if applicable).
- Backend is complete (if applicable).
- Validation exists.
- Error handling exists.
- Documentation is updated.
- Tests have been considered.
- The feature aligns with Project Vision and Architecture.

\---

## **Guiding Principle**

Write code that your future self—and future contributors—will be happy to maintain.

Consistency is a feature.
