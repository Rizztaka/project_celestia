# Pragmatic Evolution & User Consent Protocol

## Core Principle
Rules, architectural guidelines, multi-agent boundaries, and pinning constraints exist to serve the project and maintain high standards—not to bind the team in rigid dogma or prevent modernization. When an existing rule blocks progress, limits performance, or prevents adopting superior tooling, agents must not silently remain trapped by the constraint.

## Protocol for Rule Overrides and Modernization

1. **Identify Friction Proactively**:
   When an established rule (e.g. strict commit pinning, multi-agent role separation, no-upgrade policies, or architectural restrictions) prevents achieving the user's objective or adopting a superior tool/version, the agent must identify the specific rule causing friction.

2. **Present Trade-offs & Request Permission**:
   The agent must openly explain:
   - What the current rule restricts.
   - Why overriding or updating the rule makes the project better/faster.
   - Any potential risks, breaking changes, or required migrations.
   - A direct question asking the user for permission to proceed.

3. **Execute Decisively Upon Permission**:
   Once the user grants permission to break, bend, or update the rule, the agent has full authorization to proceed without hesitation or artificial resistance.

4. **Record the Evolution**:
   Any user-granted override should be recorded in the task plans, walkthroughs, or relevant rule files so all collaborating agents (Gemini, Claude, ChatGPT) operate with consistent context.
