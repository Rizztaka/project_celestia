### 2. Findings

#### Confirmed Actionable Findings

No confirmed correctness, security, or regression defects were found in the production C5d implementation across the seven reviewed paths. However, static analysis of the test and admission layers identified one **Low-severity test-determinism gap** in the PostgreSQL concurrency test suite and one **Low-severity admission-ordering behavioral edge case** worth noting:

##### 1. [Low — Test Determinism] Concurrent delete-vs-import/goal-write PostgreSQL test does not deterministically exercise the `delete-locks-first` interleaving

* **Path and function**: `apps/api/tooling/account-data.integration.test.js`, test `'coordinates deletion with an actual import and another owner-locked write'` (lines 465–487), calling `AccountDataService.prototype.delete` (`apps/api/src/platform/account-data/account-data.service.ts:40-45`).
* **Trigger and observable result**: Line 472 launches `Promise.allSettled([service.delete(ids.a, password), importer.importAccount(ids.a, ...), new GoalRepository(db).write(ids.a, ...)])`. Because `service.delete` first runs `reauthenticate()` (a separate read-only database transaction `this.repository.credential(owner)` followed by CPU-bound `await bcrypt.compare(password, credential)`) before starting the deletion transaction, whereas `importer.importAccount` and `GoalRepository.write` immediately begin their transactions and execute `SELECT id FROM users WHERE id = ${userId} FOR UPDATE`, the import and goal write nearly always acquire the `users` lock and commit *before* `repository.delete` begins its transaction. The test only asserts `expect(outcomes[0].status).toBe('fulfilled')` (line 483) and does not verify the case where `importer.importAccount` and `GoalRepository.write` block behind an already-acquired deletion lock and reject after `delete` commits.
* **Source reasoning**: In production (`apps/api/src/games/genshin/importer/importer.repository.ts:53-56` and `apps/api/src/platform/companion/goal.repository.ts:23-26`), if `repository.delete` acquires `SELECT id FROM users WHERE id = ${owner} FOR UPDATE` first and commits `tx.user.delete`, a blocked `SELECT id FROM users WHERE id = ${userId} FOR UPDATE` in `importer.repository.ts` or `goal.repository.ts` wakes up, returns `owners.length === 0`, and throws `UnauthorizedError`. Because `service.delete` performs `bcrypt.compare` before locking `users`, an uncoordinated `Promise.allSettled` tests the `write-then-delete` order rather than the `delete-then-blocked-write` order.
* **Existing tests/guards checked**: `account-data.integration.test.js:488-513` tests post-delete rejection for `nikkeAccountService`, `nikkeCharacterService`, `upsertAbyssRun`, and `eventProgress`, but runs them sequentially *after* `await service.delete(ids.b, password)` completes rather than while blocked on the `FOR UPDATE` lock.
* **Minimal correction / regression test**: If deterministic coverage of the `delete-locks-first` path is desired in `account-data.integration.test.js`, hold the transaction inside `repository.delete` after `SELECT id FROM users WHERE id=${owner} FOR UPDATE` (using the same `$transaction` proxy pattern already used in `account-data.integration.test.js:423-449`), start `importer.importAccount` and `GoalRepository.write`, release the deletion gate, and assert that `delete` fulfills while both concurrent owner-locked writes reject with `statusCode: 401` and leave zero surviving rows.

##### 2. [Low — Admission Ordering] `REQUEST_BUSY` concurrency rejections consume the owner's 60-second rate-limit tokens

* **Path and function**: `apps/api/src/core/middleware/request-admission.ts`, `protect()` (lines 129–148).
* **Trigger and observable result**: In `protect()`, `const retry = store.take(key)` (line 130) executes *before* `const release = pool.acquire(key)` (line 142) and `const sharedRelease = options.sharedPool?.acquire(socketIdentity(req))` (line 144). When the global account-data pool (`global: 2`) or shared auth pool (`global: 4` / `perIdentity: 2`) is saturated by other requests, an owner whose request is rejected with `429 REQUEST_BUSY` (`Retry-After: 1`) still has 1 token deducted from their 60-second `BoundedRateStore` (`burst: 3, refillMs: 60_000`). If the client retries after the advertised 1-second `Retry-After` interval while the pool remains busy across three attempts, the owner's rate bucket is exhausted and subsequent requests fail with `429 RATE_LIMITED` (`Retry-After: 60`) even after the concurrency pool frees up.
* **Source reasoning**: `store.take(key)` unconditionally mutates `this.entries.set(key, fullAt + this.policy.refillMs)` on line 67 of `request-admission.ts`, and `protect()` does not refund or defer `store.take(key)` when `pool.acquire(key)` or `sharedPool.acquire(...)` returns `null`.
* **Existing tests/guards checked**: `account-data.http.test.ts:197-226` and `227-252` test at most two same-owner requests after a busy rejection (staying within `burst: 3`), so the third request still succeeds without hitting `RATE_LIMITED`.
* **Minimal correction (if undesired)**: Keeping `store.take(key)` first is defensible as a deliberate DoS guard against tight `REQUEST_BUSY` polling loops, and `ARGON_PROMPT.md` explicitly notes that test controls must account for the owner's rate budget. If product policy prefers not penalizing an owner when global/shared concurrency is held by *other* owners, `BoundedRateStore` could either take tokens only when `pool.acquire` succeeds or use a separate short-window limit for busy retries (do not change this without an explicit policy decision, as existing C5c/C5d contracts document admission before work).

#### Hypotheses and Non-Resurrecting Race Observations

* **Pre-authenticated non-owner-locked writes racing across the deletion commit instant return `500` instead of `401`/`404**`:
* **Paths**: `apps/api/src/games/genshin/endgame/endgame.service.ts` (`logAbyssRun` lines 237–253, `logTheaterRun` lines 339–352), `apps/api/src/platform/companion/event.repository.ts` (`upsertTier` lines 18–29), and `apps/api/src/games/nikke/characters/character.service.ts` (`addCharacter` lines 25–52).
* **Analysis**: Unlike imports, goals, routines, focus, and plan writes (which acquire `SELECT id FROM users WHERE id = ${userId} FOR UPDATE` and map a missing user to `401` or `404`), these retained routes perform `requireAuth` (and for endgame/NIKKE character writes, `findUnique` on `genshinAccount`/`nikkeAccount`) outside a transaction before executing `upsert`/`create`. If account deletion commits in the narrow window *after* `requireAuth`/`findUnique` succeeds and *before* `upsert`/`create` executes, PostgreSQL's `FOR KEY SHARE` foreign-key check rejects the write with Prisma error `P2003` (foreign key violation). As proven in `account-data.integration.test.js:488-513`, this **cannot resurrect any deleted parent or child row**. However, because `P2003` is not caught in those services, the global error handler in `apps/api/src/app.ts:99-104` logs `Unhandled server error` via `logger.error` and returns HTTP `500 INTERNAL_SERVER_ERROR` rather than `401`/`404`.


* **Future `NikkeEquipment` writer lock granularity**:
* **Path**: `apps/api/src/games/nikke/account-data/nikke-account-data.ts:54-56`.
* **Analysis**: `nikkeAccountData.lockAndCheckDeletion` locks `SELECT id FROM "NikkeAccount" WHERE "userId" = ${owner} FOR UPDATE`, which blocks concurrent `NikkeCharacter` inserts via their foreign key to `NikkeAccount`, but does not lock `"NikkeCharacter" FOR UPDATE` (which is the immediate parent of `"NikkeEquipment"`). Under the current codebase, no route or service ever writes to `NikkeEquipment`, so no race is reachable today; if a future milestone adds `NikkeEquipment` writes, it should either lock `users`/`NikkeAccount` `FOR UPDATE` or `lockAndCheckDeletion` should also lock `"NikkeCharacter" FOR UPDATE`.



#### Documented Limitations and Product Tradeoffs (Verified Consistent with Contract)

* **Uncached identity existence read (`AuthRepository.subjectExists`) runs outside transaction-local SQL timeouts**: Documented in `docs/plans/c5d-account-data/contract.md:70-77`. On account-data routes, if `subjectExists` stalls, the 30,000 ms response deadline destroys `res` while holding the concurrency permits until the Prisma query settles.
* **Conservative rejection of compressed PostgreSQL varlena columns (`422 ACCOUNT_DATA_LIMIT`)**: Documented in `contract.md:88-93` and implemented in `account-data.repository.ts:113-121` (`pg_column_compression(field) IS NOT NULL`). Prevents decompression bombs before `::text` conversion at the cost of rejecting large TOAST-compressed legacy JSONB rows.
* **Single-process in-memory admission stores and backup-restore token validity**: Rate and concurrency pools (`request-admission.ts`) live in process memory (`trust proxy: false`), and stateless JWT revocation after deletion relies on `AuthRepository.subjectExists` returning `false` (`auth.middleware.ts:103-110`). Restoring an old database backup would recreate the `users` row and make an unexpired pre-deletion JWT valid again, which `contract.md:127-129` and `beta-readiness.md:12` explicitly track as an open production gate.

#### High-Risk Paths Checked with Zero Defects Found

* **SQL injection & identifier safety**: All table and column names in `AccountDataRepository` (`account-data.repository.ts:16, 109-110`) come from frozen code-owned allowlists (`profileTable`, `genshinAccountTables`, `nikkeAccountTables`) quoted via `identifier()`, while `owner` is bound exclusively as a parameterized `$1` value from `req.user.id`.
* **Snapshot isolation & scalar fidelity**: `AccountDataRepository.export` runs in a `REPEATABLE READ`, `READ ONLY` transaction with `timezone = 'UTC'`, `datestyle = 'ISO,YMD'`, and `extra_float_digits = 3`, casting every allowlisted column to `::text` so large integers, JSONB text, timestamps, and nulls are exported without JS number coercion or live Companion projections.
* **Cross-owner `ON DELETE SET NULL` / `NO ACTION` protection**: `checkGenshinOwnership` (`genshin-account-data.ts:192-208`) runs after `FOR UPDATE` locks on owned `genshin_accounts`, `upgrade_goals`, `genshin_characters`, and `genshin_weapons`, checking both directions (`s.userId = owner OR p.userId = owner`, etc.) and rejecting with `409 ACCOUNT_RELATIONSHIPS_UNSUPPORTED` before `prepareDeletion` or `tx.user.delete` can trigger `SET NULL` on a foreign owner's character or artifact.
* **Browser session isolation, URL revocation & focus management**: `downloadAccount` and `deleteAccount` (`apps/web/src/lib/account-data.ts`) enforce `assertCurrentSession(session)` and `signal.aborted` before and after network/DOM steps, always call `anchor.remove()` and `URL.revokeObjectURL(url)` in `finally`, and `AccountDataControls.tsx` restores focus only after `mutation.isPending` settles (`lines 45-52`).
