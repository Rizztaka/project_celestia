## Problem and outcome

**Follow-up, 2026-10-03:** the owner separately authorized focused C2b review/corrections and bounded C3a equipment implementation. Existing raw catalogs feed material totals, Today Domains, and Planner routes without proving key correctness, relationships, or game-rule accuracy. Clock activation establishes which server day applies; it does not establish what can be farmed that day. Unknown stock currently becomes zero in the material delta path, and unsupported goal data can be silently skipped.

C2b must expose trustworthy advice only for a small verified slice, with explicit reasons for unavailable targets and unknown inventory. Preserve every existing goal/import/routine record. A catalog entry's presence, TypeScript cast, or passing schema does not verify its game facts.

## Fixed scope

Inventory all ten existing Genshin static JSON files and their advice consumers, but verify/correct at most these three existing targets: **HuTao, Sethos, StaffOfHoma**. Add only the canonical material/source references needed by those targets; no new characters, weapons, boss catalog, current events, banners, or endgame coverage.

Supported advice, only when sourced: character/weapon ascension phases 0–6 and base character talent levels 1–6 within the current goal contract. Exclude talent level 0, effective constellation-adjusted levels, levels above 6, and special ascension systems. Do not expand persisted goal ranges/lifecycle in C2b. Higher talent tiers may remain archived raw data; they cannot become advice by being present in a JSON file.

These are audit candidates, not pre-approved verified records. Existing values such as `HuTao.talent.book = Ballad`, `StaffOfHoma.materialGroup = Aerosiderite`, and the talent rows named Cecilia Garden need source checks. Do not infer the correct replacements from this plan. Keep a candidate unavailable when facts cannot be established.

## Implementation order

1. **Record the inventory and evidence.** Create `task.md` before application edits and `catalog-inventory.md` listing file, consumer, purpose, trust status, and owner. Add a checked-in verification manifest for the three candidates and their dependencies, with source URL or readable local primary evidence, observed/version date when known, attributable verifier, exact supported fields/ranges, and stable content fingerprint. Record evidence before marking any entry verified. Never invent missing dates, versions, or reviewers. Preserve denied-site access restrictions and record unresolved evidence conflicts. Separate relatively stable costs from volatile event/patch schedules. Never claim whole-patch coverage.
2. **Add one typed game-owned catalog boundary.** Use existing Zod conventions. Validate finite nonnegative integer costs, exact target/material keys, unique contiguous supported phase/talent rows, tier references, supported day indices, and domain/material-group joins. Weapon ascension must represent all required material tiers/families explicitly; a misleading `billet` placeholder cannot become a verified cost. Metadata keys are not targets. Fingerprint exact verified content and required dependencies using a documented stable representation; changed dependencies also remove affected eligibility until re-reviewed. Invalid/unverified dependencies disable affected advice with a reason; basic routine tracking and imports must still boot and work.
3. **Route the bounded consumers through that boundary.** Extend `ICompanionProvider` with a narrow typed trust/cost/source view as needed. Platform code must use the provider interface. Apply eligibility to `GoalService` material totals/Today Domains and Planner Intelligence, including its calculator's current direct JSON loads. Do not leave an alternate raw-data route around the guard. Reuse existing arithmetic/allocation; no new engine or optimizer. Use neutral existing ranking fallback while upstream character-profile/ranking evidence is unverified, rather than presenting legacy scores as validated weights.
   Reuse does not preserve arithmetic defects: include every sourced cost of the selected upgrade action, including Mora and all material tiers. Do not include leveling/EXP or add crafting/conversion optimization. Source route locations, availability, and resin-per-claim rules independently of upgrade costs; existing numeric constants are not evidence. Missing route evidence disables route advice while independently verified cost totals can remain available. Allocation is a resin budget, not an assertion of guaranteed drops, remaining runs, or completion.
4. **Represent unsupported goals and unknown stock.** Keep goal creation/listing and identities intact. Advice returns per-goal availability/reason for unsupported or invalid targets/ranges instead of silently omitting demand. A mixed request may advise on verified goals but must explicitly list excluded goals and must not label its totals a complete plan. C1b provides import receipt/source/scope, not proof that an exporter observed the entire game inventory. `replacement_section` describes a database replacement; `entryCount=0` describes supplied positive entries. Neither proves missing materials have zero quantity, and the importer discards zero entries. Under the current persisted contract, absent keys remain unknown. Recorded positive quantities may support calculations on an explicitly labeled imported-stock basis; do not call them live observations. Known needed totals can be returned even when a deficit is unknown. Do not backfill completeness, change import semantics, or add persistence to recover absent zero evidence in C2b. Preserve imported unknown keys and all legacy user data. Reads remain SELECT-only.
5. **Keep placeholders unavailable.** `events.json` and `weekly-bosses.json` retain their placeholder labels. Existing advice endpoints/UI must not present placeholder or expired entries as current supported content. C2a aggregate weekly claims remain usable independently; do not add per-boss tracking, reward credit, cost/discount advice, or a Transformer cooldown. Inventory other intelligence/endgame assumptions, clearly retain their unverified legacy status, and defer engine rewrites.
6. **Finish the existing Planner presentation.** Add concise availability/unknown-stock explanations to the material, Today, route, and event panels. Preserve independent supporting-panel errors and the working Daily/Weekly tabs. No navigation redesign, equipment UI, or implementation jargon in product copy. Additive API fields may preserve callers; if an unsafe legacy numeric shape must change, migrate every caller and document the exact break instead of returning invented zero values.
